# 2026-08-30 (3) 点の作り方を本来の設計に戻す

## 何が問題だったか

点は `ranges.py` の分布域から乱数で散らしただけで、
**個々の点にその植物がある確認が無かった**。

ユーザーの本来の意図はその逆で、初日から一貫していた:

    ランダムに地点を引く → ストリートビュー（＝Mapillary）の写真を見る
      → その植物が写っている → その点を残す
      → 写っていない → 捨てて別の地点を引く

**Mapillary はこのためにあった。** 初日に Street View を捨てて Mapillary を選んだのは、
CC-BY-SA で保存・再配布できるから＝**点の裏付けとして写真を保存できるから**。
それを「図鑑写真の補完」程度に扱っていたのが取り違えだった。

## 実装したもの（トークン待ちで未実行）

| ファイル | 役割 |
|---|---|
| `src/mapillary.py` | API ラッパ。トークンは `data/.mapillary_token` か環境変数 |
| `src/land.py` | 陸地判定。`sample_points.py` から切り出し（あちらは import で処理が走る） |
| `src/verify_points.py` | 候補をランダムに引き、その地点の写真を集める |
| `src/review_candidates.py` | 候補写真を並べて目視で採否を決める |
| `src/build_verified.py` | 採用された点を集約 |

- 再開可能。判定済みの候補は再取得しない（`data/verified/<種>.json` に状態を持つ）
- **認証エラーと「写真が無い」を区別する**。
  最初これを混同していて、トークンが無効でも「この地点には写真が無い」として
  候補を延々と消費してしまう作りだった。今は即止まる
- 判定は自動化しない。画像認識に種の同定を任せると、
  誤判定した点が「確認済み」として混ざり、この方式の意味が消える

## 残作業

1. **Mapillary のトークン発行**（要手作業）
   https://www.mapillary.com/dashboard/developers → Register Application
   → `data/.mapillary_token` に貼る（.gitignore 済み）
2. `verify_points.py` を回して候補を集める
3. `review_candidates.py` で目視、採否を決める
4. `build_verified.py` → `build_atlas.py`

確認済みの点は1種あたり8点を目標にしている（`TARGET_PER_SPECIES`）。
2,785点とは桁が違うが、1点ずつ写真を見る以上これは当然で、
**点の意味が「分布の濃さ」から「実際に確認した場所」に変わる**。
